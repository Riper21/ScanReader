## 1. Контекст и границы системы

**ScanReader** — библиотека и CLI-платформа распознавания юридических документов РФ с Zero-Trust
верификацией, Fast-Path роутингом и экспортом в 1С:Предприятие / Excel.

Ключевая характеристика текущего момента: **рабочее ядро уже эксплуатируется в продакшене —
прямыми вызовами через CLI, без сервисной обвязки.** Платформа остается локальным пакетом:
инфраструктура — файловая система хостов-клиентов + **центральный корпоративный VLM-эндпоинт**
(поднят, полностью функционален, со своими очередями). HTTP-сервера, базы данных и
платформенных очередей у ScanReader **нет** (детали — раздел 13).

Рабочий контур — закрытый корпоративный периметр; входные документы содержат ПДн
(паспортные данные, СНИЛС, ИНН) — см. раздел 11.

### Предметная область: 9 плагинов типов документов «из коробки»

| Плагин (`doc_types/`) | Категория документов | Ключевые Zero-Trust проверки |
| :--- | :--- | :--- |
| `commercial_contracts` | Договоры | Стороны, ИНН/КПП, ОГРН, НДС, суммы |
| `invoices_upd` | УПД и накладные | Статус 1/2, табличные строки, ставки НДС 20/10/0 % |
| `acceptance_certificates` | Акты сдачи-приемки | Договор-основание, период, стоимость |
| `powers_of_attorney` | Доверенности | Паспорт, СНИЛС, передоверие, срок |
| `legal_claims` | Досудебные претензии | Долг, неустойка, расчет ст. 395 ГК РФ |
| `hr_orders` | Кадровые приказы | Формы Т-1/Т-5/Т-6/Т-8, оклад, даты |
| `enforcement_orders` | Приказы ИП (ФССП) | РОСП/УФССП, реквизиты сторон |
| `executive_documents` | Исполнительные листы | Серии ФС/ВС, суды, суммы взыскания |
| `salary_deductions` | Взыскания из зарплаты | Ст. 99 229-ФЗ (50 %/70 %), ст. 138 ТК РФ (20 %) |

Добавление нового типа = папка в `doc_types/` с 7 обязательными файлами + опциональный
`verification.json` (декларация проверок). Ядро не знает предметных полей (плагинная изоляция).

## 4. Интеллектуальный слой (VLM/LLM)

### 4.1 Жесткое требование протокола

Клиент работает **только по OpenAI-совместимому протоколу** (`/v1/chat/completions`).
Google Gemini напрямую не поддерживается — только через OpenAI-совместимый прокси
(OpenRouter, LiteLLM и т.п.). Эндпоинт должен быть **мультимодальным**
(изображения страниц уходят в запросе).

### 4.2 Варианты эндпоинтов

**Продакшен (актуально):** используется центральный корпоративный VLM-эндпоинт — поднят,
полностью функционален, имеет собственные очереди. Предметная необходимость — ключ
с достаточными TPM/RPM под целевую нагрузку. Локальные варианты ниже актуальны
для dev/standalone-запусков.

| Вариант | Базовый URL | Модель по умолчанию | Комментарий |
| :--- | :--- | :--- | :--- |
| **Ollama (локально, по умолчанию)** | `http://localhost:11434/v1` | `qwen2.5-vl:7b` | Основной корпоративный вариант, данные не покидают контур |
| vLLM / SGLang / LM Studio | `http://<host>:8000/v1` | `Qwen/Qwen2.5-VL-7B-Instruct` | Для пропускной способности выше одного хоста |
| OpenAI / DeepSeek / OpenRouter / LiteLLM | соответствующие `/v1` | например `gpt-4o-mini` | Облачный вариант; DeepSeek — reasoning-блоки вырезаются `_safe_parse_json` |

**Ориентировочные ресурсы GPU (7B мультимодальная модель) — только для локальных dev-запусков;
продакшен-инференс уже обеспечен центральным VLM-контуром:**
- Ollama, квантование Q4 — порядка 6–8 ГБ VRAM (или CPU — медленно, единицы минут на страницу);
- vLLM, FP16 — порядка 16–20+ ГБ VRAM (веса + KV-кэш).

### 4.3 Параметры надежности и пропускной способности (per-process)

| Параметр | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `VLM_HTTP_TIMEOUT` | 600 с | Таймаут HTTP-запроса к модели |
| `VLM_SLOT_TIMEOUT` | 120 с | Ожидание слота в RateLimiter |
| `VLM_RPM_LIMIT` | 60 | Лимит запросов в минуту к модели |
| `VLM_MAX_CONCURRENCY` | 2 | Максимальный параллелизм запросов |
| `VLM_ROUTER_CONFIDENCE_MIN` | 0.5 | Порог уверенности роутера; ниже — документ помечается unknown, а не молча уходит в чужую ветку |
| `VLM_ROUTER_OVERRIDE_MIN` | 0.85 | Минимальная уверенность роутера, при которой он может перекрыть уверенную эвристику (>= 0.90): слабое мнение деградировавшей модели не меняет верный маршрут |
| `SCANREADER_VLM_ATTEMPTS` | 2 | Повторы экстракции, если ответ без JSON |
| `SCANREADER_MAX_PAGES` | 20 | Страниц на один мультимодальный запрос (защита от переполнения контекста) |
| `ENABLE_RATE_LIMITER` | true | Вкл/выкл локальный рейт-лимитер |

**Важно для планирования:** все лимиты — **в рамках одного процесса**. При параллельном запуске
нескольких CLI/воркеров эти бюджеты не суммируются и не разделяются — реальная нагрузка
на общий ключ центрального VLM = сумма по процессам. Собственные очереди VLM-сервиса
сглаживают пики, но коллективное превышение TPM/RPM ключа возможно — контроль объединенной
нагрузки относится к платформенной обвязке (см. [REQUIREMENTS_PLATFORM_RU.md](REQUIREMENTS_PLATFORM_RU.md), QUEUE-005/ML-002).

### 4.4 Кэш ответов VLM (файловый, per-process)

- Включен по умолчанию (`ENABLE_CACHE=true`), каталог `.cache/scan_reader`.
- LRU, до 2000 записей; сброс на диск каждые 25 вставок и не реже чем раз в 30 с (вне блокировки).
- Провальные и эвристические ответы **не кэшируются** — повторный запуск обратится к модели заново.
- Между процессами кэш не координируется (нет общей БД/брокера).

## 5. OCR-слой (независимый канал верификации)

OCR — предметная необходимость, а не опция качества: без него кросс-модальный гейт для **сканов**
опирается на транскрипцию той же модели, что выполняла экстракцию. Такая сверка **не является
независимой** и помечается в отчете `gate_source=vlm_transcription` + предупреждение
`GATE_REFERENCE_FROM_VLM`. Для текстовых слоев DOCX/PDF эталон точен и бесплатен.

| Необходимость | Значение |
| :--- | :--- |
| Движок CPU | `pip install "scan-reader[ocr]"` — rapidocr-onnxruntime (~15 МБ) |
| Движок GPU | `pip install "scan-reader[ocr-full]"` — paddleocr + paddlepaddle |
| Выбор движка | `SCANREADER_OCR_ENGINE`: `auto` (быстрый поиск) / `rapidocr` / `paddleocr` |
| Включение | `SCANREADER_OCR_ENABLED=true` |
| Язык (Paddle) | `SCANREADER_OCR_LANG=ru` |
| Глубина прохода | `SCANREADER_OCR_MAX_PAGES=5` (обычно хватает первых страниц исполнит. листов) |
| Порог текстового слоя | `SCANREADER_OCR_MIN_TEXT_LENGTH=50` символов — короче значит «страница = изображение» |
| Резерв VLM-транскрипции | `SCANREADER_OCR_CROSSCHECK=true` — включается, когда OCR недоступен |
| Диагностика | `scan-reader doctor` показывает активный бэкенд |

## 6. Файловая инфраструктура (обязательные директории)

| Директория | Переменная | Назначение |
| :--- | :--- | :--- |
| `incoming/` (алиас `Входящие_документы/`) | `SCANREADER_INCOMING_DIR` | Входящие сканы для пакетной обработки; поиск: env → cwd → корень |
| `output/` | `SCANREADER_OUTPUT_DIR` | Артефакты: `{stem}_Full.json`, `{stem}_Flat.json` per документ; append-only реестры |
| `.cache/scan_reader/` | `SCANREADER_CACHE_DIR` | Файловый LRU-кэш ответов VLM |
| `data/ground_truth/` | `SCANREADER_GROUND_TRUTH_DIR` | Эталоны бенчмарка; сами проверяются на валидность ИНН/СНИЛС/БИК |
| Разрешенные корни | `SCANREADER_ALLOWED_DIRS` (`;` на Windows) | Единственные пути, доступные JSON-RPC-инструментам |
| Корень данных | `SCANREADER_HOME` | База для `.env` и относительных путей; fallback — корень проекта |

**Ограничения ввода-вывода:**

- `MAX_INPUT_BYTES = 50 МБ` — жесткий лимит размера входного файла во всех интерфейсах.
- Запись артефактов — атомарная (`_write_atomic`: временный файл + fsync + замена) — защита
  от битых файлов при сбоях питания/процесса.
- Реестры (Excel/1С) дополняются, а не усекаются.
- Имена файлов санитизируются (`sanitize_filename`) для кроссплатформенности.
- Порядок поиска `.env` (первый найденный побеждает, без override): `SCANREADER_HOME` → cwd → корень проекта.

## 7. Входные форматы

| Формат | Путь в конвейере | Эталон для гейта |
| :--- | :--- | :--- |
| PDF (скан или текстовый слой) | PyMuPDF; Dual-Zone нарезка шапки + OCR | text_layer / ocr |
| Изображения: JPG, PNG, TIFF | Pillow → как страницы-изображения | ocr |
| DOCX | python-docx / docx2txt | text_layer |
| DOC/RTF | через docx2txt (лучший случай) | text_layer |

Не поддерживаемые или поврежденные типы: статус `rejected_unsupported` / `ocr_low_confidence`
(< 150 DPI) — честный отказ вместо угадывания.

## 8. Интерфейсы и методы (полный реестр)

### 8.1 CLI (`scan-reader` / `scanreader`)

| Команда | Назначение | Ключевые опции |
| :--- | :--- | :--- |
| `run <file>` | Полный цикл: классификация → экстракция → Zero-Trust → артефакты | `--format flat\|full\|both`, `--json` (структурированный вывод) |
| `classify <file>` | Fast-Path классификация по шапке (без экстракции) | `--json` |
| `verify <json>` | Независимый Zero-Trust аудит ранее извлеченного JSON | `--json` |
| `export <dir>` | Сводные реестры 1С и многостраничный Excel из артефактов | `--format both` |
| `doctor` | Самодиагностика: модель, TTFT, токены, GPU, окружение, OCR-бэкенд | — |
| `mcp` | Запуск приватного JSON-RPC 2.0 сервера по stdio | — |

**Контракт кодов возврата (обязателен для 1С silent-интеграции):**

| Код | Значение |
| :--- | :--- |
| 0 | Обработано, блокирующих замечаний верификации нет |
| 1 | Ошибка обработки / файл не найден |
| 2 | Ошибка аргументов CLI |
| 3 | Расхождение или гейт не выполнился — требуется ручная проверка |
| 4 | Суммы восстановлены regex-сканером, а не прочитаны моделью (`heuristic_fallback`) |

Логи CLI направляются в stderr, машиночитаемый вывод — в stdout (совместимо с конвейерами).

### 8.2 Python API

```python
from scan_reader import LegalDocPlatformFacade
from scan_reader.verifier import ZeroTrustAuditor, VerificationStatus

facade = LegalDocPlatformFacade()
result = facade.process_single_document("scan.pdf")   # doc_type, data, quality_score_percent, raw_text
report = ZeroTrustAuditor.audit_document(data=..., doc_type=..., raw_ocr_text=...)
report.status  # ZERO_TRUST_VERIFIED | PARTIALLY_VERIFIED | GATE_NOT_EXECUTED | ...
report.issues  # [VerificationIssue(code, message)]
```

### 8.3 JSON-RPC 2.0 по stdio (приватный протокол)

Запуск: `scan-reader mcp`. Формат — один JSON-объект на строку.

| Метод RPC | Эквивалент CLI | Назначение |
| :--- | :--- | :--- |
| `tools/list` | — | Список инструментов |
| `tools/call` → `scan_document` | `run` | Полный цикл распознавания и аудита |
| `tools/call` → `classify_document` | `classify` | Экспресс-роутинг шапки |
| `tools/call` → `verify_legal_data` | `verify` | Изолированный алгоритмический аудит JSON |
| `tools/call` → `run_benchmark` | батник 3 | Эталонная оценка по Ground Truth |
| `tools/call` → `export_results` | `export` | Консолидация в Excel и 1С |

**Границы протокола (важно):** это **не** официальный MCP. Нет Content-Length framing и
рукопожатия `initialize` — стандартные MCP-клиенты (Claude Code, Codex) не подключатся без
адаптера. Протокол предназначен для доверенных внутрипериметровых интеграций; все пути
ограничены `SCANREADER_ALLOWED_DIRS`, размер — `MAX_INPUT_BYTES`.

### 8.4 Лаунчер и операторские батники

| Точка входа | Сценарий |
| :--- | :--- |
| `launcher.py` | Drag & Drop файла/папки на скрипт; системный диалог (tkinter); интерактивный fallback при unknown-категории; пакетная обработка; бенчмарк; диагностика VLM |
| `scripts/windows/0_ДИАГНОСТИКА_VLM_И_ТОКЕНЫ.bat` | Проверка эндпоинта и токенов |
| `scripts/windows/1_ОБРАБОТКА_ДОКУМЕНТОВ.bat` | Основной цикл оператора |
| `scripts/windows/2_Открыть_папку_Результаты.bat` | Открытие `output/` |
| `scripts/windows/3_ЗАПУСК_БЕНЧМАРКА_GROUND_TRUTH.bat` | Эталонное тестирование |
| `scripts/windows/4_ЭКСПОРТ_В_EXCEL.bat` | Сводный Excel-реестр |

| Директории | `SCANREADER_OUTPUT_DIR`, `SCANREADER_INCOMING_DIR`, `SCANREADER_GROUND_TRUTH_DIR`, `SCANREADER_HOME` | `./output` / `./incoming` / `./data/ground_truth` / корень проекта |
| Доступ | `SCANREADER_ALLOWED_DIRS` | пусто (JSON-RPC к файлам не имеет корней) |
| OCR | `SCANREADER_OCR_ENABLED`, `SCANREADER_OCR_ENGINE`, `SCANREADER_OCR_LANG`, `SCANREADER_OCR_MAX_PAGES`, `SCANREADER_OCR_MIN_TEXT_LENGTH`, `SCANREADER_OCR_CROSSCHECK` | true / auto / ru / 5 / 50 / true |
| Прочее | `LOG_LEVEL`, `NO_COLOR` | INFO / отключено |

Устаревшее: `VLM_TIMEOUT` — алиас `VLM_HTTP_TIMEOUT`, будет удален.

## 11. Безопасность и персональные данные

| Необходимость | Реализация |
| :--- | :--- |
| Закрытый контур | Основной сценарий — локальные модели (Ollama/vLLM); данные не покидают периметр |
| ПДн (152-ФЗ) | Входные документы: паспорт, СНИЛС, ИНН, банковские реквизиты. Требуется операторская дисциплина: доступ к `incoming/`, `output/`, кэшу по принципу минимальных прав |
| Маскирование в логах | `mask_secret()` в `get_logger()` — обязателен для всех модулей; фильтр покрывает `record.args`, а не только `record.msg` (утечка через `logger.info("токен %s", secret)` исключена) |
| Ограничение файлового доступа | JSON-RPC работает только внутри `SCANREADER_ALLOWED_DIRS` |
| Целостность файлов | Атомарная запись + fsync; поврежденные артефакты исключены |
| Секреты в CLI | Ключи не выводятся; `doctor` печатает маскированные значения |

## 13. Сервер, база данных, очереди — статус «как есть»

| Слой | Статус | Текущая реализация | Следствие для эксплуатации |
| :--- | :--- | :--- | :--- |
| **Сервер** | **Отсутствует** | Приватный JSON-RPC 2.0 по stdio (per-process), CLI, лаунчер | Нет HTTP-эндпоинта, нет TLS, нет auth на транспортном уровне. Каждый потребитель запускает свой процесс |
| **БД** | **Отсутствует** | Файловые артефакты JSON (append-only), файловый LRU-кэш, Excel-реестры | Нет разделяемого состояния; кэш и рейт-лимиты не координируются между процессами; история обработки = содержимое `output/` |
| **Очереди** | **Отсутствуют (платформенные)** | Локальный `RateLimiter` (RPM, слоты) + лимит параллелизма в рамках процесса; очереди исполнения запросов — на стороне центрального VLM-сервиса (внешний контур) | Пакетная обработка синхронна в CLI; параллельность нескольких операторов/процессов против общего ключа VLM не управляется централизованно |

**Вердикт по текущим сценариям:** перечисленного достаточно для эксплуатационных контуров
«оператор — CLI» (продакшен, центральный VLM), «1С silent-запуск по расписанию»
и «доверенный stdio-агент».
Границы текущей архитектуры (что **не** поддерживается сейчас):

- нет MCP-совместимости (нужен адаптер для Claude Code/Codex);
- нет REST/gRPC API — интеграция только через CLI-выход, Python-импорт или stdio;
- нет разделяемого кэша/бюджетов между процессами и командами;
- нет веб-интерфейса и истории задач вне файловой системы;
- нет ретраев на уровне «очереди заданий» (только `SCANREADER_VLM_ATTEMPTS` внутри одного документа).

Эскалация этих границ — предмет отдельного плана (см. `docs/plans/`).

## 14. Контрольный чек-лист запуска (минимальный боевой набор)

1. Python 3.9+ установлен; `py -3 --version` отвечает.
2. Пакет установлен из этого репозитория: `py -3 -m pip install -e ".[ocr]"`;
   проверка: `py -3 -c "import scan_reader; print(scan_reader.__file__)"` → путь в этот репозиторий.
3. Ключ центрального VLM получен, лимиты TPM/RPM достаточны под целевую нагрузку;
   `OPENAI_BASE_URL` / `AI_MODEL_NAME` в `.env` указывают на центральный эндпоинт
   (локальный Ollama — только для dev).
4. `.env` создан из `.env.example` и лежит в корне проекта (или задан `SCANREADER_HOME`).
5. `scan-reader doctor` — зеленый: модель отвечает, TTFT и токены в норме, OCR-бэкенд виден.
6. Директории существуют и доступны на запись: `incoming/`, `output/`, `.cache/scan_reader/`.
7. Для JSON-RPC: заполнен `SCANREADER_ALLOWED_DIRS` (только доверенные корни).
8. Для операторов: батники `scripts/windows/` с CRLF-окончаниями, консоль UTF-8 (`chcp 65001`).
9. Smoke-тест: `scan-reader run "<пробный документ>" --json` → код возврата 0 или 3,
   в `output/` появились `_Full.json` / `_Flat.json`.
10. Приемочный бенчмарк: `scan-reader run_benchmark` (или батник 3) на эталонном наборе —
    метрики не деградировали относительно `docs/measurements/risks-1.0.0.json`.
